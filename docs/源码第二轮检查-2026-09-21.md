# 源码第二轮检查：缺陷与验证记录

日期：2026-09-21。对象：当前工作区源码 1.5.1。范围：功能连接、数据异常、录音生命周期、链接抓取、原生编译、打包引用和官网检查。

本轮确认 **8 类缺陷，尚未修复**，其中 4 类建议优先处理。现有完整测试通过，但补充的异常与并发场景仍能复现问题。这说明现有测试对这些场景存在覆盖缺口，不能据此宣布当前版本没有 Bug。

本轮只新增检查文档和复现材料，没有修改产品代码、替换安装版、生成 DMG、推送或发布。测试使用隔离目录、模拟音频设备和测试密文；网络复现只连接本进程创建的本地测试服务，没有读取真实密钥或启动真实麦克风。

### R1：启动录音缺少等待状态与并发保护

`startRecording()` 进入时检查 `recordingStatus === 'idle'`，但等待权限和 `getUserMedia()` 时仍保持 `idle`。只有拿到设备、创建 MediaRecorder 并开始录音后，才改成 `recording`。

触发：在授权或设备初始化完成前再次点开始，或从两个录音入口快速触发开始。两次调用都通过入口检查，分别获得音频流，但共享的 `mediaStream`、`mediaRecorder` 被后一次覆盖。后续停止只操作最后一份引用。

实际渲染页面复现结果：打开 2 路模拟流；点击停止后仍有 1 路 track 为 live、1 个 recorder 为 recording，而界面 `isRecordingActive()` 已返回 false。没有开启真实麦克风；复现证明的是流引用与停止逻辑存在遗漏。

建议：在第一次异步等待前进入 `starting` 状态，统一禁用两个入口；采用启动代次或取消标记，并确保过期请求返回的流立即释放。停止、失败和页面销毁均清理对应会话持有的全部资源。

### R2：读取失败被当成空密钥库

`readCredentialsVault()` 把文件读取失败、解密失败和 JSON 解析失败统一变成 `[]`。只要 `safeStorage.isEncryptionAvailable()` 为 true，列表仍返回 `ok: true`。新增/修改接口没有区分“库本来为空”和“已有库暂时打不开”，直接基于这个空数组写回。

触发：已有密钥库的解密操作失败，但加密服务仍报告可用，此时新增一条密钥记录。

临时文件复现结果：列表显示成功且 0 条，保存返回成功，原有密文被新库替换。这个行为可能使之后恢复解密能力时，也找不回原库内容。本轮没有访问用户的实际密钥库。

建议：读取返回明确的不存在、正常、损坏、解密不可用状态；存在旧库且无法完整读取时禁止覆盖，保留原文件并展示可恢复错误。加密本身抛错的路径也应进入统一错误处理。

### R3：录音写入失败后没有重试材料

`finalizeRecording()` 在保存接口返回失败时调用 `discardRecordingDraft()`，之后无条件清空 `audioChunks`、`recordingTranscript`，恢复 idle。用户看得到失败提示，但没有重试保存或导出本次录音的入口。

触发：目录不可写、磁盘空间不足，或录音超过主进程当前 200 MiB 限制等保存失败场景。

复现结果：模拟 `write_failed` 后，音频缓存数量为 0、草稿数量为 0、转写内容也被清空。不能把这种失败视为已安全结束。

建议：保存失败进入可恢复状态，保留 Blob、草稿、转写与时长；提供重试/另存/明确放弃。音频文件和元数据的保存结果应分别检查，成功后再清理缓存。

### R4：公网地址检查后发生第二次解析

`validatePublicHttpUrl()` 用 `dns.promises.lookup()` 检查地址后只返回 URL；`fetch(current)` 没有使用已核验的目标地址，会重新解析域名。若可控域名在两次解析间改变结果，校验通过的公网地址与实际连接的地址可以不同。

受控复现：校验阶段返回 `8.8.8.8`，连接阶段返回 `127.0.0.1`；请求实际到达本进程的本地 HTTP 测试服务，检查接口仍返回 `ok: true`。没有连接任何其他本机服务或外部服务器。这确认了内网访问限制的缺口，不代表用户已遭遇攻击。

建议：把经过验证的解析结果绑定到本次连接，同时保留正确的主机名/TLS 校验；每次重定向重新执行同样策略。网页、图标及其他使用同一检查函数的网络路径应统一复核，避免只补其中一处。

### R5：有效 JSON 不等于有效业务数据

`loadJson()` 只处理 JSON 解析错误，没有验证返回类型。指令和录音初始化随后直接调用 `.map()`。例如键值为 `{}` 时，JSON 解析成功，但 `.map()` 抛错，整个 `initWorkspace()` 后续初始化中断。

实际渲染页面复现：分别把 `notch-home-commands` 或 `notch-recordings` 设为 `{}`，重新载入后都出现 `loadJson(...).map is not a function`，`window.NotchWorkspace` 未建立。空白正常数据作为对照组能正常初始化，没有页面错误。

这是损坏或不兼容数据的恢复缺口，不表示正常版本每次保存都会生成这种数据。

建议：在存储边界验证数组及每个条目的结构；异常数据保留备份、显示恢复说明，单个功能的数据问题不应阻断其余功能初始化。

### R6：收到响应头后提前清掉超时

`inspectLink()` 等到 `fetch()` 返回响应后立即清除超时，稍后才调用 `readResponseText()`。如果服务器快速返回响应头，但正文持续不结束，原本 8 秒的超时不再覆盖这段等待。

复现把同一计时参数缩短为 30ms：90ms 后操作仍未结束，AbortSignal 也未取消；手动结束测试响应体后才完成。

当前界面先保存链接、再后台补全，因此这个问题主要导致标题/图标补全长期挂起和请求资源滞留，不能描述成所有链接保存都会卡死。

建议：总时限覆盖解析、响应头和正文消费；及时取消响应体，并把流读取异常转换成明确的可恢复结果。图标下载还应使用有上限的流式读取。

### R7：文件删除失败后仍删除元数据

单条删除等待 `deleteRecording()`，但忽略返回的 false；批量删除同样忽略各文件的返回结果。随后无条件从资料库数组移除条目并保存。

触发：音频目录或文件不可删除。复现返回 false 后，资料库条目仍变成 0 条；音频文件实际可能还留在磁盘上，用户却失去了对应管理入口。

建议：区分成功、文件本来不存在、权限/磁盘错误；仅移除确认成功的条目。失败条目保留，并给出可重试反馈。元数据保存失败也不能伪装成完整成功。

### R8：后台补全覆盖后来的手动编辑

添加链接后，网页抓取在后台进行。用户可以在它完成前改标题；返回处理没有检查标题是否已被用户修改，仍然赋值为 `inspected.title`。

复现：先添加链接，保留尚未完成的网页读取；把标题修改为用户指定的名称，再返回网页标题，最终名称被改回网页标题。

建议：记录手动编辑状态或字段版本，后台补全只填补尚未被用户编辑的字段；异步结果应检查对应对象和请求版本仍有效。

## 3. 仍存在的疏漏与未覆盖范围

- 第一轮确认的源码/安装版不一致、未跟踪产品模块、`output/` 未忽略、工作区备份失败无反馈、旧 IPC 校验不统一，仍需处理。本轮没有把这些重复计入新增 8 类缺陷。
- 官网页脚仍写 `macOS 14+` 和旧名“浮岛”，与源码的最低 macOS 13 配置及当前名称不一致。下载与网站元信息仍指上游仓库；将来建立私库时需要按该仓库用途明确处理。
- 菜单栏遮挡仍是已有未解决问题；最新柔焦玻璃没有获得用户明确的视觉验收。本轮原生参数和生命周期测试通过，不替代真实桌面观感验收。
- 没有重新生成或安装 DMG，没有验证所有 macOS、外接屏和睡眠/锁屏组合，也没有对每种 AI 工具执行真实账户接入。
- 本轮是有范围的源码复核，未证明已找出所有缺陷。已经有足够证据表明应先补异常处理、并发保护和相应测试，再继续叠加功能。

建议修复顺序：R1/R2/R3 的资源和数据保护 → R4 网络边界 → R5–R8 恢复与交互 → 第一轮指出的基线和维护问题。私库备份可保存为明确标注待修复的源码基线，修复过程逐项提交。
