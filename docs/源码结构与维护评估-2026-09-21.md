# 悬浮岛：源码结构与维护评估

评估日期：2026-09-21。目标：为上传 GitHub 私有仓库和后续维护整理代码现状。

后续补充：同日第二轮已完成完整桌面检查及异常场景复现，确认了 8 类待修复缺陷。新增结果见 [源码第二轮检查](源码第二轮检查-2026-09-21.md)；下文保留第一轮的检查范围与原始结论。

本次做了源码结构审查、Git 文件范围检查、安装版文件对比和单元测试。没有修改产品代码、替换本机应用、打包、创建仓库或推送。本报告是一次有范围的评估，不是全部功能或安全性已验收的证明。下列文件数量为生成本报告前的快照。

## 1. 判断

项目存在明显技术债，但现有证据不足以支持推倒重写。已经有独立的领域服务、原生能力封装、数据校验和回归测试，值得保留。

当前最影响可靠性的，是源码、运行中的安装版和 Git 提交没有形成一致的可复现基线；其次是窗口状态和界面逻辑集中、实际视觉验收不足、历史约束分散在多处。不能用对话长度或文件行数推算 Bug 数量，也不能用“测试全绿”推断所有使用场景都正常。

建议顺序：筛选并保存当前源码快照 → 对齐源码与安装版 → 固定验收场景 → 按模块逐步整理。私库可以先保存明确标记为“尚未完成验收”的源码，不必等所有问题修完，更不必先做一次大重写。

## 2. 代码是什么

这是一个面向 Apple Silicon Mac 的本地桌面工作台。当前打包配置为 arm64、最低 macOS 13；实际跨系统兼容性仍需要实机验证。它不是 iOS 应用。

桌面应用采用 Electron 44、原生 HTML/CSS/JavaScript，没有桌面渲染层构建步骤。独立官网位于 `website/`，采用 React 19 与 Vinext。桌面运行数据主要保存在本机，没有项目自建的同步后端；天气、AI 工具连接和可选转写等功能会访问外部服务。

```text
Electron 主进程 main.js
├── 主窗口：折叠岛、悬停预览、展开工作台
├── 速览窗口：quick-island
├── 独立提醒窗口、系统状态窗口
├── 本机服务：AI 工具、项目抽屉、录制、剪贴板、存储等
└── macOS 原生辅助模块
        ↕ 有限的 IPC 接口
preload.js / window.notchAPI
        ↕
renderer/ 各页面、组件、状态与样式

website/：独立官网，不参与桌面窗口渲染
```

| 模块 | 主要文件 | 职责与维护注意点 |
| --- | --- | --- |
| 主进程与窗口 | `main.js`、`system-ui-guard.js` | 启停、窗口位置与层级、焦点、收放、菜单栏、系统浮层避让及 IPC；主进程仍承载大量其他功能 |
| 渲染与界面 | `renderer/app.js`、`workspace.js`、`quick-island.js`、`styles.css` | 待办、布局、设置、笔记、录制、快捷入口及跨窗口同步；部分逻辑依赖共享变量与脚本加载顺序 |
| 可独立验证的规则 | `main-services.js`、`renderer/domain.js` | 数据规范化、提醒规则、窗口/剪贴板策略等；是继续拆分的现有基础 |
| AI 工具接入 | `ai-code-runtime.js`、`ai-tools.js`、`ai-code-connectors.js`、`code-provider-specs.js`、`code-tool-paths.js`、`ai-code-plugin.js` | 确认单选工具、安装检测、连接与状态归一化；各工具的实际能力不能由 Codex 状态代替 |
| Codex 任务 | `codex-float.js`、`codex-task-state.js`、`codex-process.js`、`codex-activity-cache.js`、`codex-lifecycle-http.js` | 额度、生命周期、重启恢复、缓存与本机事件鉴权；Hook 脚本位于 `scripts/` |
| 本地功能服务 | `project-drawer*.js`、`quick-launch.js`、`computer-status.js`、`weather-service.js` | 文件分类元数据、应用快捷入口、电脑状态及天气缓存 |
| 活动与提醒 | `island-activities.js`、`island-status-window.js`、`island-system.js`、`renderer/notification.*`、`renderer/island-popup.css` | 录音/计时状态、任务完成和系统提示；涉及多窗口生命周期与计时 |
| 外观与尺寸 | `appearance-settings.js`、`appearance-surface.js`、`appearance-native.js`、`window-size-settings.js`、渲染层对应文件 | 偏好迁移、跨窗口同步、玻璃几何与原生桥接 |
| 原生能力 | `native/appearance-glass.mm`、`native/system-status-helper.swift` | AppKit 玻璃、窗口/系统信息；额外背景模糊使用非公开的 `CABackdropLayer` / `CAFilter` 能力 |
| 检查与分发 | `tests/`、`scripts/build-*.js`、`build/`、`.github/workflows/` | Node/Electron 测试、原生编译、应用签名、打包、官网和 Release 流程 |

桌面主要命令：`npm start`、`npm test`。`prestart` 编译原生辅助模块，因此从干净目录运行还需要 Xcode Command Line Tools 和 Node.js 开发头文件；不能只复制 JavaScript 就认为环境完整。桌面打包与发布仍须遵守项目的独立授权约束。

## 3. 数据边界

实际默认 `userData` 沿用 `~/Library/Application Support/Dynamic Panel`，以兼容旧版。显示名称改成“悬浮岛”不代表数据目录也已改名。用户也可以选择可迁移工作区；两者不能混为一个目录。

| 数据 | 当前存放方式 | 后续修改必须保留的约束 |
| --- | --- | --- |
| 待办 | LocalStorage 的 `notch-todo-data` | `P0`–`P3` 内部结构保持兼容，类别显示名称单独保存 |
| 笔记、链接、指令、录制元数据、布局 | LocalStorage；`workspace.json` 保存工作区快照 | 需要明确恢复、失败反馈与迁移行为，不按界面标题随意改存储键 |
| 音频、剪贴板图片 | 工作区的 `recordings/`、`clipboard-images/` | 文件与元数据需要保持一致；不能把图片 dataURL 塞进 LocalStorage |
| 外观、尺寸、工具选择、项目分类 | `userData` 中各自的 JSON 文件 | 保留版本迁移、失败后原值与重启恢复语义 |
| 密码与 API Key | `safeStorage` 加密的本机文件或环境变量 | 不随源码、截图、日志或安装包上传 |
| AI 活动与接入鉴权 | 本机活动缓存、Hook 配置及生命周期 token | 属于用户环境；源码只保留实现和无真实凭据的示例 |

主进程的通用 JSON 写入已经采用临时文件后重命名，密钥库也有原子替换逻辑。问题并非“所有保存都不可靠”，而是部分调用方没有把保存失败呈现出来。

## 4. 已确认的重点问题

### A. 源码、安装版和提交不同步：优先解决

| 对象 | 检查结果 |
| --- | --- |
| 当前源码 `package.json` | `1.5.1` |
| `/Applications/悬浮岛.app` 内的 `package.json` | `1.4.17` |
| 当前分支最近一次提交 | `e69ccca`，2026-08-31，准备 `v1.0.5` |
| 已跟踪文件的本地改动 | 38 个；文本差异新增 3,373 行、删除 2,360 行 |
| 未跟踪文件 | 10,102 个，包含产品源码和大量调试产物 |

逐文件比较确认：安装版的 `main.js`、`main-services.js`、`preload.js` 和抽查的外观配置模块与源码一致；但 `renderer/app.js`、`renderer/workspace.js`、`renderer/styles.css`、`renderer/index.html` 不同。

因此这不只是忘记改版本号。直接从当前源码运行，不能假定得到与当前安装版相同的全部界面；只推送现有提交，也不会包含新增功能。24 个顶层 JavaScript 模块仍未跟踪，其中包括 AI、外观、项目抽屉和系统服务。

处理建议：保留两份现状，先列出差异对应的产品行为，再形成一份经过检查的权威源码。不要用整包覆盖来消除差异，也不要在不同安装备份之间继续挑文件拼装后声称可复现。

### B. 上传范围需要先整理

`output/` 约 4.6 GB、包含 9,926 个未跟踪文件，有安装备份、DMG、测试环境和大量截图；当前 `.gitignore` 没有忽略它。`视频分析/` 约 17 MB，也没有忽略。

相反，`.cache/`、`node_modules/` 等已忽略。不能因为看到了很多未跟踪文件，就把它们全部删除：其中也有 111 个源码/配置类文件需要审查后纳入版本控制。

当前 `origin` 指向上游 `xiaopu-ai/TO-DO-Panel`，本次未访问远端，也未确认其可见性或用户将来的私库地址。私库备份目标应单独核对，不能直接向现有上游推送。

`.git` 本地占用约 876 MB。进一步核查发现，超大的应用/DMG 对象出现在本地工具检查点引用中，不能据此断言普通分支推送会发送这些对象。当前分支及标签可达历史的主要大文件是官网演示 GIF。后续上传应选择明确的分支，避免镜像全部内部引用；本次没有清理历史或检查点。

### C. 职责集中，容易造成跨功能回归

| 文件 | 行数 |
| --- | ---: |
| `main.js` | 4,193 |
| `renderer/app.js` | 3,955 |
| `renderer/workspace.js` | 2,397 |
| `renderer/styles.css` | 5,116 |

`main.js` 中有 83 处 `ipcMain.handle/on` 注册。行数本身不是 Bug，但同一文件还处理窗口/焦点、存储、密钥、媒体、链接与系统集成，修改影响范围较大。窗口收放又同时受多个状态标记、计时器、异步回调与不同窗口影响。

应先拆职责边界，例如窗口协调、工作区持久化、录制/转写；保持现有外部行为与数据结构。仅按行数平均拆文件、一次切换框架或大量改名，不能解决这些依赖问题。

### D. 测试通过与用户实际验收存在缺口

菜单栏遮挡在 README 中明确列为未解决。近期柔焦玻璃修改也尚未得到用户明确的视觉验收，不能标成已完成。

原生测试会检查模糊参数、图层位置、焦点与释放行为，这些检查有价值，但不能证明背景在实际屏幕上看起来就是目标柔焦效果。非公开原生能力还存在不可用时的降级路径，需要把实际降级外观和支持范围列入验收。

部分测试通过字符串匹配或从 `main.js` 截取函数片段到 VM 中运行，例如 `tests/renderer-structure.test.js`、`tests/notch-preview-main.test.js`。这能拦住一些回归，但不等于完整应用集成验证，并使重构受到函数文本位置的约束。

### E. 保存失败的反馈缺失

`main.js` 的 `workspace:save-data` 在内容超过 8 MiB 或磁盘写入失败时返回 `false`；`renderer/app.js` 开头的两秒自动备份只忽略异常，没有检查这个返回值，也没有告知用户快照保存失败。

这是已确认的错误反馈缺口。它不等于已经证明 LocalStorage 数据丢失，但可能让用户误以为可迁移工作区已经同步成功。应单独修复并验证磁盘不可写、容量限制和目录切换场景。

### F. 接口校验标准不一致，需要专项复核

新接口普遍使用 `isIslandSender` 校验窗口、主 frame 和本地页面；部分旧接口，例如工作区保存及密钥操作，没有同等的发送方检查。现有窗口已开启隔离/沙盒、禁用 Node 集成，并阻止页面导航和新窗口，这些防护需要保留。

本次没有证明可被利用的攻击链。应把“所有敏感 IPC 使用统一的发送方与参数策略”作为后续审查项，而不是把少数接口已校验理解成整体已覆盖。

### G. 文档与持续检查需要收敛

README 中既有两档宽度与默认 1040px 的说明，也残留速览固定 1240px 的描述；AGENTS 与 README 对部分工具的接入能力也有不同表述。历史 ADR 已声明推翻，后续必须遵守这个状态，不能继续按旧原生重写方案开发。

当前桌面测试工作流由手动运行或版本标签触发，普通开发提交/PR 没有对应的桌面检查入口。官网另有主分支变动后部署 Pages 的工作流；迁到私库时，应明确它是纯备份仓库还是仍负责发布，避免照搬上游部署目标。

## 6. 建议怎么做

### 第一步：形成可上传、可回退的源码快照

保留当前目录和安装版，先不改功能。补齐忽略规则，区分产品源码、必要资源、文档与本机产物；保留 LICENSE、第三方说明和锁文件。逐项审查准备提交的内容，避免 `git add .` 把安装备份和个人截图一起纳入。

将当前可用源码保存为明确标注现状的提交，再向确认过的私有仓库推送指定分支。该提交代表备份基线，不代表稳定版，也不需要顺带打标签、发 Release 或部署官网。本次尚未执行这些操作。

### 第二步：对齐运行版本并固定验收依据

先解释源码与安装版差异，确定要保留的行为，记录菜单栏遮挡、柔焦观感等尚未解决项。然后从干净的源码副本和独立测试数据启动验证，确认不依赖旧缓存、未跟踪模块或历史安装补丁。

最少固定下列验收场景，并为失败保留复现步骤：

| 场景 | 需要确认 |
| --- | --- |
| 首次运行与重启 | 工具未确认时不自动连接；已确认的选择、尺寸、外观与数据正常恢复 |
| 窗口完整流程 | 折叠 → 悬停预览 → 速览 → 工作台 → 收回，焦点、中文输入和状态角标一致 |
| 系统与显示器变化 | 外接屏、菜单栏高度/缩放、锁屏、休眠、全屏及临时浮层后的恢复 |
| 数据保存 | 待办、笔记、录音保存和目录切换；错误可见、失败后原数据可恢复 |
| 资源生命周期 | 摄像头、麦克风只由主动操作开启，并按对应退出/结束条件释放 |
| 任务与提示 | 运行/等待/失败/完成、队列计时、重启恢复和切换工具不串数据 |
| 实际外观 | 用固定背景和真实窗口检查柔焦、纯黑、圆角及收放残留，保留用户确认的基准图 |

### 第三步：小步整理，逐项验证

先处理保存失败反馈等可独立修复的问题，并复核敏感 IPC。随后提取窗口协调模块，统一状态转换和清理时机；再整理存储、录制/转写与渲染层功能模块。

每次只完成一个边界清晰的改动，先保留相关回归检查，再修改，检查通过后单独提交。涉及行为的改变和纯结构整理分开提交；视觉改动必须带实际对比，不能仅凭参数测试宣布完成。

### 第四步：让接续开发依赖仓库事实

README 继续作为当前产品行为准绳；AGENTS 聚焦开发约束和文档入口，减少复制产品细节。另维护简洁的架构/数据说明和已知问题清单，历史设计保留日期与失效标记。

每个后续任务记录：问题如何复现、影响哪些模块、接受的行为、改了什么、测了什么、还缺什么。新任务先读这些文件和当前 Git 差异，再动代码。这样长对话被压缩后，关键约束仍能从源码、提交、测试和文档中恢复。

## 7. 可用于下次接续的简述
